# Notes v4: RFC 011 provider onboarding flow

Working notes for [011](./011-provider-onboarding-flow-improvements.md). Not the RFC itself. v4 builds on the [v2 notes](./xxx-notes-011-provider-onboarding-flow-improvements-v2.md) and replaces its bearer connection secret with **mutual TLS run inside an ordinary HTTPS WebSocket**. The PM-side authenticates with certificates from an **owner CA** kept in the owner's workspace; the Provider-side authenticates with a pinned server key. The Provider-side only needs an HTTPS endpoint that supports WebSockets. v4 states its trust boundary explicitly: **the owner's workspace is the owner's responsibility.** It records what the investigation of [v3](./xxx-notes-011-provider-onboarding-flow-improvements-v3.md) and several review rounds of v4 turned up, and compares all four versions (see "Findings" and "Comparison").

## Terminology

- **PM-side**: the PM instance (kcp + PM operator). May be behind NAT; dials out.
- **Provider-side**: the service provider (controllers + portal in its runtime cluster). Serves the connection API and reconciles on the PM-side.
- **Owner**: whoever controls the workspace that holds the `Provider` object and its connection Secret on the PM-side.
- **Connection**: the relationship between one `Provider` object on the PM-side and one connection record on the Provider-side, identified by `connectionID`. Created by registration, ended by deletion on either side. **The Provider-side's state for a connection belongs to that connection and is never inherited by another one.**
- **Onboarding token**: a single-use, short-lived token from the Provider's portal. It contains the Provider's URL. Unchanged from v2.
- **Owner CA**: a CA kept in the connection Secret in the owner's workspace (generated by default, or supplied by the owner). The Provider-side pins it at registration as the connection's identity.
- **Connection certificate**: a short-lived client certificate the connector issues itself from the owner CA. Used in the inner TLS handshake.
- **Server key**: the keypair the Provider-side's connection server uses in the inner TLS handshake. The PM-side pins its public key at registration.
- **Session**: one WebSocket to the Provider's base URL, carrying one **inner mTLS** connection between the connector and the connection server. The connection API and the tunnel run inside sessions.
- **Access token**: the bound SA token the Provider-side uses against kcp. Unchanged from v2, where it's called the SA token.
- **Connector**: the PM-side component that opens sessions, delivers access tokens and kcp's CA bundle, and holds the tunnel. Where it runs is an open item.
- **`ProviderOnboardingRequest`**: as in v2, minus re-onboarding (see "Resources").

## Problem

Unchanged from v2: the Provider-side must reconcile on any number of PM instances, the PM-side may be behind NAT and opens every connection, the user gets a token from the Provider's portal, and both sides must recover from restarts and outages without manual steps.

What v4 changes is how the PM-side proves "I own this connection" after registration.
- **v2**: a long-lived bearer secret, sent on every call, visible to every TLS-terminating hop.
- **v3**: short-lived kcp SA tokens, verified against kcp's signing keys. This removed the secret, but tied every connection to kcp's key management, which turned out to be fragile (see "Findings").
- **v4**: certificates from an owner CA, proven in a TLS handshake that runs end to end between the connector and the Provider's connection server, through whatever ingress the Provider has.

**Constraints.**
- **Assume as little as possible about the Provider's infrastructure.** Many Providers sit behind cloud L7 load balancers, CDNs, WAFs, or a central platform team's ingress. TLS passthrough or client-certificate-verifying ingresses can't be required.
- **Assume nothing about how PM operates kcp's PKI.** PM must stay free to rotate kcp's CAs, add shards and change its edge. The design must not depend on kcp's rotation procedures or on operator-specific artefacts like merged CA bundles.

## Trust boundary

**The owner's workspace is the owner's responsibility.** It holds the `Provider` object, the connection Secret (with the owner CA) and, under RFC 006, more credentials that reach the provider workspace. Whoever gets into it can act as the owner. v4 doesn't try to defend a connection against its own owner's compromise; it makes sure that:
- **nothing outside the owner's workspace** can take over an existing connection: not a stolen onboarding token, not a compromised Provider portal account, not the Provider's ingress or CDN;
- **leaks are bounded in time** where possible (short-lived connection certificates and access tokens);
- **Provider-side state can't be hijacked** by registering a new connection for the same workspace.

Consequence: an attacker with the owner CA can do whatever the owner's connection can, including presenting a fake kcp to the Provider-side (see "kcp's CA bundle"). That's owner compromise, in the same category as leaking the workspace's other credentials.

## Core idea

- **TLS inside a WebSocket.** The connector opens an ordinary HTTPS WebSocket to the Provider's base URL. The ingress terminates that **outer** TLS as usual, routes by path, and from then on forwards opaque WebSocket frames. Inside the WebSocket, the connector and the connection server run a second, **inner** TLS 1.3 handshake with mutual authentication. The ingress sees only encrypted inner bytes: it can neither read nor impersonate either side.
- **The connection's identity is the owner CA.** The Provider-side pins it at registration. The connector issues itself short-lived certificates from it (e.g. valid 24h) whenever needed, so nothing it presents ever expires in a way that needs the Provider-side's help. The owner can back up the CA and so control the connection's durability.
- **The Provider-side's identity is a pinned server key**, returned at registration over web PKI.
- **kcp's CA travels with the credentials**, as in v2. The connector sends the CA bundle PM's own components use for kcp, so it follows PM's rotations automatically.
- **No re-onboarding of existing connections.** A connection can only be changed through a session authenticated by its owner CA. Registration only ever creates new connections, and a new connection never inherits Provider-side state.
- **Revocation is a database delete.** The Provider-side checks the connection record on every handshake and request.

```
connector ══ outer TLS (web PKI, terminated at ingress/CDN) ══▶ ingress ──▶ connection server
          ╚═ WebSocket: GET /v1/connections/{id}/session ═════════════════════╝
               ╚═ inner TLS 1.3: owner-CA cert ⇄ pinned server key ═══════════════╝
                    ╚═ HTTP: connection API, or the tunnel ═══════════════════════╝
```

## Provider-side prerequisites

- **An HTTPS endpoint at the base URL from the token that supports WebSocket upgrades** and long-lived connections: idle timeouts above the session ping interval (e.g. > 60 s), and a maximum connection age the connector can reconnect after. Any ingress, cloud L7 load balancer or WebSocket-capable CDN qualifies. A WAF must let binary WebSocket frames through after the upgrade.
- **A connection server** that terminates the inner TLS. It's a normal mTLS HTTPS server behind a WebSocket listener. The Provider SDK should ship it.
- **A server key** for the inner TLS, kept in a Secret on the Provider-side.
- **State keyed by `connectionID`**, never by the PM-side's addressing alone (see "Provider-side state").
- **Owner notifications and controls.** The portal notifies the token owner of every registration and every owner CA change (in the portal and by email), and lets the owner freeze or delete their connections.

Not required: a second hostname, TLS passthrough, client-certificate verification at the ingress, cert-manager, or a CA on the Provider-side.

## Flow overview

1. **Get a token.** As in v2.
2. **Create the request.** As in v2.
3. **Create or reuse the `Provider`.** As in v2, except that an already registered `Provider` is refused (see "Resources").
4. **Register.** The request generates the owner CA, or uses the one the owner supplied, then calls `POST /v1/connections` on the token's URL with the onboarding token, the addressing and the owner CA's certificate. It gets back the `connectionID` and the connection server's public keys, and stores them in the connection Secret. No kcp credential is sent at this point.
5. **Deliver credentials.** The connector issues itself a connection certificate, opens a session and `PUT`s an access token and kcp's CA bundle.
6. **Open the tunnel.** The connector opens a second, long-lived session and runs the tunnel inside it.
7. **Confirm kcp is reachable.** The request asks for the connection's status until the Provider-side reports that it reached kcp. Only then is the request `Ready`. From here on, the Provider-side has **claimed** the provider workspace.
8. **Refresh credentials.** The connector `PUT`s a fresh access token and the current kcp CA bundle, periodically and after every reconnect. After the claim, the Provider-side may also rotate its own token (see "Provider-side token self-rotation").
9. **Offboard.** Deleting the `Provider` calls `DELETE` in a session.

Steps 5, 6 and 8 handle every restart and outage, of any length: the connector can always issue itself a new certificate.

## Design

### Onboarding token

Unchanged from v2: `pm1.<base64url(Provider base URL)>.<tokenID>.<tokenSecret>`, single-use, short-lived, stored in a Secret, with the URL inside so nothing is ever sent to the wrong host. Trust in the base URL comes from web PKI, or from the `Provider`'s `spec.remote.caBundle`.

Two additions:
- **The portal must never put tokens in URLs**, which end up in browser history, proxy logs and referrer headers.
- **The portal hands the token over as a command, not a manifest.** Offer `kubectl create secret generic … --from-literal=token=…`, or apply it directly. A "copy as Secret manifest" button invites committing the token to git.

### Registration

The only call outside a session. Plain HTTPS on the base URL, so the outer TLS is all that protects it. It carries nothing secret except the onboarding token, which is spent by the time anyone could reuse it.

```
POST /v1/connections
Authorization: Bearer <tokenID>.<tokenSecret>
{
  "idempotencyKey": "<ProviderOnboardingRequest UID>",
  "clusterID": "<logical cluster name of the provider workspace>",
  "frontProxyURL": "https://...",
  "transport": "tunnel" | "direct",
  "ownerCA": "<PEM certificate of the owner CA>"
}
→ 201 {
  "connectionID": "...",
  "serverKeys": [ "<PEM SPKI>", ... ],           // connection server's public keys; the PM-side pins them
  "anchorRotationRequiresToken": false           // Provider's choice (see "Owner CA rotation")
}
```

- **One-step registration.** As in v2: the request waits until the workspace and SA exist, then registers with real addressing.
- **Only new connections.** There's no `previousConnectionID`. Registration never touches an existing connection (see "No re-onboarding").
- **No access token in `POST`.** Behind a TLS-terminating ingress or CDN, that would be a live kcp credential in plaintext at the edge (finding 10). Every access token goes inside the inner TLS.
- **`serverKeys` is trustworthy** because the response arrives over the outer TLS to the URL inside the token, authenticated by web PKI (or `spec.remote.caBundle`). It's a list, so the Provider-side can rotate its server key with overlap.
- **Idempotency is bound to the owner CA.** `POST` is keyed on `(tokenID, idempotencyKey)`. A retry returns the same `connectionID` **only if `ownerCA` matches the first attempt**; a different CA is refused. If the response is lost and the token has expired, a retry within a bounded window (as in v2) still returns the record. The response contains nothing secret, so a replay of a logged request gains nothing. v2 has a replay hole here (finding 9).
- **Addressing is immutable**: `clusterID` and `frontProxyURL` are fixed at registration. Changing them means a new connection.
- **The owner CA's certificate**, not its key, is all that leaves the PM-side.

### Owner CA and connection certificates

- **Default: generated per connection** by the request controller (e.g. ECDSA P-256, valid 10 years) and stored in the connection Secret. **Optional: supplied by the owner** through a Secret reference on the request, for owners who want it from their own PKI, or backed up and managed like any other key material.
- **The connector issues itself connection certificates** from the owner CA: short-lived (e.g. 24h), EKU `clientAuth` only, no DNS or IP SANs. They're kept in memory, or cached in the Secret. A new one can be issued at any time, so a certificate's expiry never needs the Provider-side.
- **Backing up the owner CA is the owner's choice and responsibility.** With a backup, a lost connection Secret is recoverable: restore it, and the connector carries on with the same connection. Without one, a lost Secret means a new connection.

### Owner CA rotation

**Active and desired CA.** Two places hold a CA:
- the **active** CA, in the connection Secret: the one the Provider-side has pinned, certificate **and** key. The connector manages it as its own copy;
- the **desired** CA: the owner's Secret referenced by `ownerCASecretRef`, or, for a generated CA, a new CA the connector writes into the connection Secret as `desired`.

The owner can simply **overwrite** their Secret with a new CA, without knowing anything about overlaps. The connector still holds the active CA, so it can always authenticate the rotation. Without this split, an owner replacing their CA in place would destroy the only key the Provider-side trusts, and with no re-onboarding, the connection would be lost.

**Procedure**, whenever desired ≠ active:
1. The connector issues itself a certificate from the **active** CA, opens a session, and calls `PUT /anchor` with the desired CA's certificate.
2. The Provider-side stores it as **pending**. Certificates from both CAs are accepted.
3. The connector issues itself a certificate from the **desired** CA and opens a session with it. That successful handshake proves the PM-side holds the new key, so the Provider-side **promotes** the new CA and drops the old one.
4. The Provider-side closes sessions still authenticated with old-CA certificates. The connector switches its own sessions, the tunnel included, right after promotion, so this is a brief reconnect at most.
5. The connector copies the desired CA into the connection Secret as the new active CA.

If the `PUT /anchor` response is lost, the old CA still works and the connector retries. If the new CA is never used, the pending entry expires (e.g. after 24h) and the connection stays on the old CA. If the connector crashes partway, it compares the pinned CA (from `GET`) with active and desired on restart and resumes at step 1 or 3.

**When it happens.** A generated CA is rotated on demand (e.g. an annotation on the `Provider`, or a suspected leak) and before it expires. An owner-supplied CA is rotated whenever the owner changes their Secret. Rotations are rare by design.

**Lock-out.** Whoever holds the active CA's key can rotate to their own CA, after which the legitimate PM-side can't authenticate any more. Under the trust boundary that's owner compromise, like `DELETE`. But unlike a leak with a deadline, the attacker *keeps* the connection and its Provider-side state. Mitigations:
- the Provider-side **notifies the owner of every anchor change** (portal and email);
- the owner can **freeze or delete a connection in the Provider's portal**, a portal-authenticated owner action. It also covers a lost CA without a backup;
- **optionally**, a Provider can require a fresh onboarding token on `PUT /anchor` (`anchorRotationRequiresToken`, announced at registration). A stolen CA alone then can't lock the owner out, at the cost of a portal step per rotation. It's the Provider's choice, not mandatory.

### Sessions

```
GET /v1/connections/{id}/session        (WebSocket upgrade, on the base URL)
  └─ inner TLS 1.3 handshake
       client: connection certificate (from the owner CA)
       server: self-signed certificate for its server key
       ALPN:   "h2" or "http/1.1"
  └─ HTTP inside the inner TLS
```

- **Provider-side.** The upgrade handler checks that connection `{id}` exists, wraps the WebSocket as a `net.Conn`, tags it with `{id}`, and hands it to a listener. On that listener runs a normal HTTPS server with `ClientAuth: RequireAnyClientCert` and a verification callback that:
  1. checks connection `{id}` (from the outer path) still exists;
  2. verifies the client certificate chain with `x509.Verify` against a pool holding **only that connection's owner CA** (and a pending one during rotation), including validity and EKU `clientAuth`.

  Every inner request must also name the same `{id}` in its path. Deleting the connection closes its sessions.
- **PM-side.** The connector's HTTP client has a custom dialer: open the WebSocket, wrap it as a `net.Conn`, run the TLS client handshake over it. The verification callback checks that the server certificate's public key is one of the pinned `serverKeys`. In Go that means `InsecureSkipVerify: true` plus a verification callback, a well-known footgun if written ad hoc. Both callbacks belong in one small, tested helper in the Provider SDK.
- **Credentials don't depend on the tunnel.** The connector keeps one session for API calls and a separate long-lived one for the tunnel. If either breaks, the other is unaffected. HTTP/2 lets the API session be reused for many calls.
- **Path routing.** The outer path contains the `connectionID`, which isn't secret. Ingresses can route, rate-limit or log per connection without seeing anything inside.

### Connection API (inside a session)

```
GET /v1/connections/{id}
→ 200 { "kcpReachable": true, "lastError": "", "serverKeys": [ ... ],
        "ownerCA": "<fingerprint of the pinned CA>", "pendingOwnerCA": "<fingerprint, or empty>" }

PUT /v1/connections/{id}/credentials
{
  "token": "<fresh access token>",
  "expirationTimestamp": "...",
  "kcpCABundle": "<PEM>"                      // the CAs PM's own components use for kcp; empty = web PKI
}
→ 204

PUT /v1/connections/{id}/anchor               # owner CA rotation (see "Owner CA rotation")
Authorization: Bearer <fresh onboarding token>   # only if the Provider requires it
{ "ownerCA": "<PEM certificate of the NEW owner CA>" }
→ 202                                         # pending until a handshake with a certificate from it

GET /v1/connections/{id}/tunnel               (WebSocket upgrade inside the inner TLS; the tunnel protocol)

DELETE /v1/connections/{id}
→ 204
```

- **Readiness gate.** `GET` reports whether the Provider-side has reached kcp. The request becomes `Ready` only after `kcpReachable` is `true`, so a wrong CA bundle or an unreachable kcp fails registration visibly. `kcpReachable` and `lastError` cover **every** kcp endpoint the Provider-side uses (front-proxy and shard virtual-workspace URLs), not only the first call.
- **No kcp-specific verification on the Provider-side.** The Provider-side doesn't need to understand kcp's tokens or keys to authenticate the PM-side. It uses the access token only to talk to kcp.

### kcp's CA bundle

- **What the connector sends**: the CA bundle PM's own components use to verify its kcp endpoints, i.e. whatever is in the kubeconfig the connector itself uses for `frontProxyURL`, plus whatever covers the shard virtual-workspace hosts. The Provider-side verifies the front-proxy and every endpoint-slice URL against it, end to end through the tunnel.
- **It follows PM's rotations automatically.** The connector reads it fresh and sends it with every `PUT /credentials`. During a PM-side CA rotation, the bundle PM's own components trust is the one Providers get. If PM's own trust in its kcp works, the Provider-side's does too. Nothing depends on kcp-operator artefacts, published ConfigMaps or rotation procedures.
- **How the Provider-side uses it**: it rebuilds its kcp clients when the bundle changes:

  ```go
  cfg := &rest.Config{
      Host: conn.FrontProxyURL,
      TLSClientConfig: rest.TLSClientConfig{CAData: conn.KcpCABundle}, // empty = web PKI
      Dial: tunnel.DialContext,
  }
  ```

  When `CAData` is set, client-go trusts only that bundle, not the system roots. multicluster-runtime derives the per-endpoint clients from this base config.
- **Who can change it**: only a session authenticated by the owner CA. So a fake kcp needs the owner CA, which is owner compromise (see "Trust boundary"). The onboarding token, the Provider's portal and the Provider's edge can't change it.

### No re-onboarding

v2 let a new request with `previousConnectionID` re-onboard an existing connection using only an onboarding token. That token comes from the Provider's portal, outside the owner's workspace. Combined with a CA bundle delivered by the connection, a stolen token or a compromised portal account could take over an existing connection and point it at a fake kcp (finding 7). v4 removes re-onboarding:
- **Changes to an existing connection** (credentials, kcp CA bundle, owner CA rotation, deletion) only happen inside a session authenticated by the owner CA.
- **Registration only creates new connections.**
- **A lost owner CA without a backup** means: delete the `Provider` (or create a new one), and register a new connection. The old record on the Provider-side can't be deleted with the lost key; the owner deletes it in the Provider's portal, or the Provider-side garbage-collects connections without sessions for a long time (e.g. 90 days).
- **A server key rollover missed during a long outage** is recovered without re-onboarding: the connector re-reads `serverKeys` from the base URL (`GET /v1/connections/{id}/server-keys`, plain HTTPS, web PKI). That's as trustworthy as registration, and only used after the pinned keys fail.

### Provider-side state

- **Everything the Provider-side keeps for a connection is keyed by `connectionID`**: provisioned resources, their credentials, mappings to consumer objects.
- **A new connection never inherits state from an old one**, even with the same `clusterID` and `frontProxyURL`. Otherwise registering a second connection for someone else's workspace (with a stolen token or a compromised portal account) and serving a fake kcp through it could make the Provider-side deprovision real resources, or write their credentials into the fake kcp.
- **Moving state from an old connection to a new one** (e.g. after a lost owner CA without a backup) is a Provider-specific migration with the owner's explicit consent, out of scope here.

### Credentials and rotation

- **Send parts, not a kubeconfig**, as in v2.
- **The PM-side mints, the Provider-side holds**, as in v2: the connector `PUT`s a fresh access token at about half its TTL and after every reconnect.
- **Long-lived anchor, short-lived everything else.** The owner CA is long-lived and stays in the owner's workspace. Connection certificates (hours) and access tokens (hours) are short-lived and re-issued freely.
- **Keep the access-token TTL short (e.g. 1 hour).** In PM's kcp deployments, deleting the SA doesn't revoke tokens already issued (finding 2), so the TTL is the revocation window for kcp access if `DELETE` never arrives.
- **Access tokens never pass a TLS-terminating hop.** They only travel inside the inner TLS.
- **No static kubeconfig for remote `Provider`s**, as in v2. The owner's workspace holds no long-lived credential for the provider workspace.

### Provider-side token self-rotation

After the claim (step 7), the Provider-side may mint its own access tokens instead of waiting for the connector:
- **RBAC**: `create` on `serviceaccounts/token`, restricted with `resourceNames` to its own SA, in the provider workspace. The Provider controller creates it (RFC 006 already owns the SA and RBAC).
- **It's an optimisation.** The connector's `PUT` stays the baseline: a Provider-side whose token expired during an outage can't mint a new one with it. The connector's next `PUT` recovers it.
- **Revocation** is deleting the SA and RBAC. Tokens the Provider-side minted itself live until they expire (finding 2), so it must keep their TTL short too.

### What each credential exposes

| Credential | Lifetime | Stored at | If stolen |
|---|---|---|---|
| Onboarding token | minutes, single-use | PM-side Secret until spent; hash on the Provider-side | The thief can register **their own** new connection under the owner's portal account, including one that claims the owner's `clusterID`. It gets no access to existing connections or their Provider-side state; it's a separate tenant fed by whatever kcp the thief presents, billed to the owner's account. The owner is notified. |
| Provider portal account | long-lived | Provider-side | Same as issuing tokens, plus whatever the portal allows (billing, deleting connection records). Can't take over an existing connection or its state. |
| Owner CA key (active) | long-lived, owner-controlled | Owner's workspace (connection Secret) | **Owner compromise**: full connection identity, including pushing a fake kcp CA bundle, and rotating to the thief's own CA to lock the owner out (unless the Provider requires a token for rotations). Same category as the workspace's other credentials. The owner is notified of anchor changes. Recovery: rotate the owner CA first, or freeze or delete the connection in the portal. |
| Connection certificate and key | hours | Connector memory (or cache) | Valid until it expires (e.g. 24h). Can't issue more. Same powers as the owner CA meanwhile. |
| Provider's server private key | long-lived, rotatable | Provider-side Secret | Only useful together with control of the path between connectors and the connection server (the Provider's own ingress or CDN, or DNS for the base URL). Then the thief can impersonate the Provider-side to connectors and receive their access tokens. Rotate the server key (overlap) and re-check the edge. |
| Outer TLS / ingress / CDN | — | Provider's edge | Sees the onboarding token at registration (already spent) and opaque session bytes. Can drop or delay traffic, or answer `server-keys` refetches during a missed rollover. Can't read access tokens or impersonate either side otherwise. |
| Access token | hours (keep it short) | Provider-side | As in v2: access to the provider workspace and the APIExport virtual workspace, within RFC 006 RBAC, until it expires. Deleting the SA doesn't end this early in PM's current kcp deployments. |

### Threat model: how credentials get stolen

**The owner CA key** lives in the owner's workspace; protecting it is the owner's responsibility (see "Trust boundary"). The usual paths:

| How | Notes |
|---|---|
| **Read access to the connection Secret** | Anyone with `get`/`list` on Secrets where it's stored: workspace admins, GitOps tools, other controllers with wildcard Secret permissions. |
| **Backups and etcd snapshots** | kcp's etcd and backup tools contain the Secret. Without encryption at rest it's just base64. |
| **A compromised connector** | The connector reads every connection's owner CA. Code execution in it, a supply-chain compromise of its image, or root on its node exposes **all** connections at once. The highest-impact path. |
| **Dumps** | `kubectl get secret -o yaml` pasted into a ticket, support bundles, audit logging at `RequestResponse` level for Secrets. |
| **Insiders** | PM administrators. |

**The onboarding token.**

| How | Notes |
|---|---|
| **A compromised portal account** (phishing, password reuse) | The most likely path. The attacker doesn't steal a token; they **issue their own**. With no re-onboarding and per-connection state, it only yields new connections. |
| **Handling by people** | Tokens pasted into chat, email or tickets, picked up by clipboard managers, seen in screen shares, or left in browser history if the portal puts them in URLs. |
| **Committed to git** | A user saves the token Secret as a manifest and commits it. |
| **Ingress or CDN logs on the base URL** | TLS is terminated there, so the token is visible in plaintext. It's spent by then; CA-bound retries stop replays. |

**Ranked by likelihood × impact:**
1. **The connector or its node.** Less likely, but every connection is exposed at once.
2. **The owner's workspace (RBAC, backups, dumps).** The owner's responsibility; same exposure as the workspace's other credentials.
3. **A compromised portal account.** Likely, but limited to new connections billed to the owner's account.
4. **Server key plus control of the Provider's edge.** Needs two compromises on the Provider-side.
5. **Logged tokens or requests.** Harmless.

**Mitigations.**
- **PM-side / owner:**
  - keep connection Secrets where only the connector can read them, and never in the provider workspace, which the Provider-side's own SA can reach;
  - enable kcp etcd encryption at rest, and encrypt backups or exclude these Secrets from them;
  - owners who need durability back up their owner CA themselves, or supply it from their own PKI;
  - later: owner CA keys in a KMS or HSM, with the connector only requesting signatures for its short-lived certificates.
- **Provider-side:** key all state by `connectionID`; protect the server key like any TLS key; rotate it with a generous overlap.
- **Portal:** MFA, no tokens in URLs, a list of issued and used tokens, owner notifications on registrations and owner CA changes, freezing or deleting connections, and a command instead of a manifest for the token Secret. GitOps users should use Sealed Secrets or External Secrets.
- **Protocol:** no re-onboarding, CA-bound idempotent retries, and no kcp credentials outside the inner TLS.

### Transport

As in v2: a dial proxy, end-to-end TLS to the real kcp URLs, a `Shard`-based allow-list, ping/pong liveness, an existing library (remotedialer or Konnectivity), and an optional `direct` mode. The differences:
- The tunnel runs inside a session: outer WebSocket → inner mTLS → the tunnel library's own protocol (for remotedialer, a WebSocket upgrade on `/v1/connections/{id}/tunnel` inside the inner TLS).
- kcp traffic is thus inside **three** TLS layers: the outer (to the ingress), the inner (to the connection server), and the end-to-end TLS to kcp, verified against the kcp CA bundle from the connector. The extra CPU is negligible next to what the connection does.
- Session pings run at the outer WebSocket level, so ingresses see traffic and don't time the connection out. The tunnel library's own liveness checks run inside.

```yaml
apiVersion: providers.platform-mesh.io/v1alpha1
kind: ProviderOnboardingRequest
metadata:
  name: my-provider-2026-10-08
spec:
  tokenSecretRef: { name: my-provider-token, key: token }
  ownerCASecretRef: { name: my-owner-ca }            # optional DESIRED CA; generated if absent. Overwrite it to rotate.
  provider:
    name: my-provider                                # created if missing; refused if already registered
    spec:
      remote:
        caBundle: ""                                 # optional, for a private CA on the Provider's base URL
        transport: Tunnel
status:
  phase: Ready                                       # WaitingForProvider → Registering → VerifyingKcp → Ready | Failed
  providerRef: { name: my-provider }
  connectionID: "..."
---
apiVersion: v1
kind: Secret
metadata:
  name: my-provider-connection                       # owned by the Provider; readable only by the connector
type: Opaque
stringData:
  ca.crt: "<ACTIVE owner CA certificate>"            # the one the Provider-side has pinned
  ca.key: "<ACTIVE owner CA private key>"            # always the connector's own copy, also for owner-supplied CAs
  desired.crt: "<generated CA awaiting rotation>"    # only for generated CAs, only during a rotation
  desired.key: "..."
  serverKeys: "<pinned PEM SPKIs of the connection server>"
  url: https://provider.example.com/pm               # base URL from the token
  connectionID: "..."
```

- **How the request treats `provider.name`**:

  | The `Provider`... | The request... |
  |---|---|
  | doesn't exist | creates it, waits for the workspace and SA, then registers |
  | exists, not registered (a leftover from a failed attempt, or created by hand) | reuses it and registers |
  | exists and is registered | **refuses**. Changes to a live connection happen through the connector. To start over, delete the `Provider` |
  | exists, but isn't a remote `Provider` (e.g. a ManagedProvider) | refuses |

- `Provider.status.connection` mirrors `url` and `connectionID`. The `Provider`'s conditions are `Registered`, `KcpReachable`, `CredentialsValid` and `TunnelConnected`.

### Restart and failure semantics

| Scenario | Behavior |
|---|---|
| PM-side restarts | The connector reads the connection Secret, issues itself a certificate, opens sessions, `PUT`s credentials and the kcp CA bundle, and reopens the tunnel. |
| Provider-side restarts | Sessions drop; connectors reconnect and `PUT`. |
| Outage of any length | Nothing the PM-side needs expires: the connector issues a new certificate from the owner CA and reconnects. |
| Ingress drops a long-lived session (idle timeout, maximum connection age, redeploy) | The connector reconnects, as for any tunnel drop. Session pings keep idle timeouts from triggering. |
| PM rotates kcp's CA, adds shards or changes its edge | Nothing to coordinate: the next `PUT` carries the CA bundle PM's own components now trust. |
| `POST` response lost | The same request retries with the same token, idempotency key and owner CA: same `connectionID`. A replay with a different CA is refused. |
| Wrong or incomplete kcp CA bundle | `kcpReachable` is `false` with the TLS error. During registration the request stays in `VerifyingKcp` and fails after a timeout; later, `KcpReachable=False` on the `Provider`. Fix PM's trust; the next `PUT` repairs it. |
| Owner overwrites their CA Secret | The connector still holds the active CA, rotates to the new one (see "Owner CA rotation"), and switches its sessions. No user step beyond the overwrite, unless the Provider requires a token. |
| Owner CA rotation response lost | The old CA still works. The connector retries `PUT /anchor`. |
| New owner CA never used | The pending entry expires; the connection stays on the old CA. |
| Connector crashes during a rotation | On restart it compares the pinned CA from `GET` with active and desired, and resumes. |
| Thief with the active CA rotates to their own CA | The legitimate connector can't authenticate; the owner is notified of the anchor change. The owner freezes or deletes the connection in the portal and registers a new one. Prevented if the Provider requires a token for rotations. |
| Server key rotated | Connectors pick up the new key from `GET` during the overlap. A connector that missed the whole overlap re-reads `serverKeys` from the base URL. |
| Connection Secret lost, owner CA backed up | Restore the Secret; same connection. |
| Connection Secret lost, no backup | Delete the `Provider` (or create a new one) and register a new connection. The old Provider-side record is deleted by the owner in the portal, or garbage-collected. Provider-side state isn't inherited. |
| Connection deleted on the Provider-side | Session handshakes are refused. The `Provider` gets `CredentialsValid=False`. Recovery is a new connection. |
| Connector reconnects while the old tunnel is still open | As in v2. |
| Provider-side runs multiple replicas | As in v2: a session lands on one replica, which owns it. Railgrid's edges provider is a working example of Lease-based routing between replicas (`internal/tunnel/registry.go`, `remote.go`, `connman.go`). |

### Offboarding and revocation

- **Deleting the `Provider`** triggers a finalizer that calls `DELETE` in a session, then cleans up the SA and RBAC (RFC 006). The connection Secret is garbage-collected with the `Provider`.
- **An unreachable Provider-side doesn't block deletion forever**, as in v2.
- **Deleting the connection on the Provider-side** takes effect immediately: open sessions are closed and new handshakes are refused. No CRL or OCSP is needed.
- **kcp access** ends when the last access token expires, unless `DELETE` arrives and the Provider-side discards it first. In PM's current kcp deployments, deleting the SA doesn't end it earlier (finding 2).

## Findings

Findings 1 to 6 came up while checking v3 against kcp, kcp-operator and PM's deployment (2026-10-07/08). Findings 7 to 11 came up while reviewing v4 (2026-10-08). Several apply to every version.

1. **kcp bound tokens carry the cluster and the SA UID.** The claims are nested under `kubernetes.io`: `clusterName` (a kcp addition), `namespace`, and `serviceaccount.{name, uid}`. `sub` doesn't include the cluster, so it isn't unique across workspaces. Legacy Secret-based tokens use a flat `kubernetes.io/serviceaccount/clusterName` claim instead. Sources: `kcp/vendor/k8s.io/kubernetes/pkg/serviceaccount/claims.go:53-94`, `legacy.go:65`, `kcp/pkg/server/filters/serviceaccounts.go:70`.
2. **In PM's kcp, deleting an SA doesn't revoke its bound tokens.** **This affects v2, v3 and v4.**
   - kcp-operator always passes `--service-account-lookup=false` to every shard (`kcp-operator/internal/resources/compiledrootshard/deployment.go:232`, `compiledshard/deployment.go:271`). A kcp carry patch then skips the SA existence and UID check (`claims.go:196`). PM deploys kcp through kcp-operator (`pm-helm-charts/charts/infra/templates/kcp/`).
   - kcp itself has supported cross-shard SA lookup since v0.32, with a 1-minute cache (`kcp/pkg/server/serviceaccount/cache.go`, `pkg/shardlookup/ttl_cache.go`). The operator's flag dates from 2025-08 (commit `cf810d8`), before that existed.
   - So v2's statement "revoking the SA cuts off the Provider-side even if `DELETE` never arrives" doesn't hold today.
   - Not yet checked on a running PM cluster.
3. **Each shard has its own SA signing key.** kcp-operator issues one cert-manager certificate per shard (RSA 4096, valid 1 year, renewed 7 days before expiry; `kcp-operator/internal/resources/shard/certificates.go:125`). Every shard and the front-proxy trust all shards' public keys (`utils/authentication.go:82`). The issuer is kcp's default, `https://kcp.default.svc`, for every shard.
4. **kcp signing-key rotation has no overlap.** The same certificate is both the signing key and the verification key, and kcp reads it only at startup (a static key getter in the vendored `jwt.go`). When a shard restarts with a renewed key, it signs with the new key at once. Whether renewal creates a new key depends on cert-manager's `rotationPolicy`; recent cert-manager versions default to `Always`. This is what made v3 fragile: every connection on that shard would have to re-onboard.
5. **kcp serves its JWKS per workspace through the front-proxy.** `kubectl get --raw /openid/v1/jwks` with a workspace kubeconfig works, and the `kid` of a freshly minted token matches a key in it (tested on 2026-10-08). So v3's key distribution would have been solvable without reading Secrets. Finding 4 is what rules v3 out, not key distribution.
6. **Railgrid's edges provider** uses bound SA tokens as the only credential after enrolment, with Lease-based tunnel routing. Its agent refreshes a token by presenting the current one, so an agent offline for longer than the 24h TTL needs a new join token. That's the power-off budget every version here avoids. Its tunnel uses `revdial`, which opens a new connection per dial; the notes reject that option. For the far end of its tunnel it mostly trusts the authenticated agent (plain HTTP to the edge's Kubernetes API through the tunnel); it pins only SSH host keys, write-once, with changes resolved by a person.
7. **A connection-supplied kcp CA bundle plus token-only re-onboarding lets outsiders present a fake kcp.** **This affects v2 and v3.** Both let `PUT /credentials` set the kcp CA bundle, and in tunnel mode the connector controls the Provider-side's whole network path to kcp. Whoever holds the connection identity can take over the tunnel, `PUT` their own CA bundle and answer the Provider-side's dials with a fake kcp. The Provider-side then reconciles against state the attacker controls. Getting that identity takes either:
   - the connection secret or key, which lives in the owner's workspace. v4 accepts this as owner compromise (see "Trust boundary");
   - **or just a stolen onboarding token, via re-onboarding with `previousConnectionID`**, which needs nothing from the owner's workspace. v4 removes re-onboarding, and keys Provider-side state by connection so a new connection for the same workspace can't hijack it.
8. **kcp-operator signs every serving certificate with one CA.** The front-proxy, root-shard, shard and virtual-workspace serving certificates are all issued by `<rootshard>-server-ca` (`kcp-operator/internal/resources/frontproxy/certificates.go:123`, `rootshard/certificates.go`, `shard/certificates.go`, `virtualworkspace/certificate.go:122`; name from `resources.go:481`). That CA is valid 10 years and renewed 30 days before expiry (`sdk/apis/operator/v1alpha1/common.go:27-28`). Useful context for what the connector's CA bundle contains in PM today, but v4 doesn't depend on it.
9. **v2's retry rule lets a replayer get a working secret.** v2 honours registration retries for 24h, keyed on `(tokenID, idempotencyKey)`, and each retry issues a fresh connection secret. Both keys appear in the request, so anyone who logged a `POST` can replay it within the window, get a valid secret, and invalidate the legitimate one. v4 binds retries to the first owner CA and returns nothing secret.
10. **The registration body exposed a live kcp credential at the edge.** v2, v3 and earlier v4 drafts sent the first access token in the `POST` body. Behind a TLS-terminating ingress or CDN, that's a kcp credential in plaintext at a hop the PM-side doesn't control (and, in v2, the connection secret on every later call too). v4 sends access tokens only inside the inner TLS.
11. **kcp-operator's merged CA bundle is not a general trust source.** `<rootshard>-merged-ca-bundle` (`tls.crt` = the server CA plus the user's `caBundleSecretRef`) only exists when `spec.caBundleSecretRef` is set, which PM doesn't do, and it's only used for the `external-logical-cluster-admin-kubeconfig`, not by kcp's own components (`rootshard/ca_bundle.go`, `pkg/controller/rootshard/controller.go:212-217`, `shard_types.go:84-91`). It's not feature-gated. Commit `406169b` ("Deprecate Bundles") removed the unrelated `Bundle` resource and its `ConfigurationBundle` feature gate. Earlier v4 drafts considered publishing or pinning such bundles; v4 now takes kcp's CA bundle from PM's own trust instead.

## Changes from v2

| v2 | v4 | Why |
|---|---|---|
| Long-lived bearer connection secret | Owner CA in the owner's workspace; short-lived connection certificates; mutual TLS inside a WebSocket | Nothing secret crosses a TLS-terminating hop after registration |
| Provider-side authenticated by web PKI on every call | Web PKI at registration, then the pinned server key end to end | A compromised ingress or CDN can't impersonate the Provider-side |
| First access token in the `POST` body | All access tokens inside the inner TLS | Finding 10 |
| Re-onboarding with `previousConnectionID` and an onboarding token | No re-onboarding; changes only through owner-CA-authenticated sessions | Finding 7 |
| Provider-side state keyed implicitly | State keyed by `connectionID`, never inherited | A new connection for the same workspace can't hijack state |
| `PUT /credentials` carries the kcp CA bundle | Unchanged in principle, now sourced explicitly from PM's own trust | Follows PM's rotations without depending on kcp procedures; safe because only the owner CA can change it |
| Request is `Ready` after `POST` | Request is `Ready` after the Provider-side has reached kcp | A wrong CA bundle fails registration visibly |
| Retry issues a new secret to whoever sends it | Retry bound to the first owner CA; nothing secret returned | Finding 9 |
| Secret rotation is an open item | Certificates rotate automatically; the owner CA rotates via `PUT /anchor` | No rotation protocol for routine use |
| "Revoking the SA cuts off the Provider-side" | Revocation is `DELETE`, plus a short access-token TTL | Finding 2 |
| Implicit trust model | Explicit: the owner's workspace is the owner's responsibility | Defines what the design does and doesn't defend |

## Rejected alternatives

All of v2's rejected alternatives still apply, except "mTLS" itself. Several of the following were earlier drafts of v4.

- **mTLS directly on a dedicated hostname.** A second hostname reached through TLS passthrough, or through an ingress that verifies client certificates and forwards them in a header, plus a cert-manager CA so ingresses could verify. Assumes too much about the Provider's edge: cloud L7 load balancers can't pass TLS through, passthrough bypasses CDNs and WAFs and often needs a security exception, and verifying ingresses need fragile configuration.
- **Pinning kcp's CA at registration**, changeable only with the owner's key and a fresh onboarding token. Protects against a stolen connection key, but every kcp CA rotation then needs a portal step per connection, and PM must stay free to rotate.
- **A PM-published trust bundle the Provider-side follows** over TLS verified with its current pin. Rotations follow automatically, but only if PM publishes bundles with an overlap before every switch: the design would depend on kcp's deployment procedures being done right. kcp-operator's merged bundle isn't a reliable source for it either (finding 11).
- **A PM-owned front key, with the connector terminating the Provider-side's TLS to kcp.** Fully independent of kcp's PKI and resistant to a stolen connection key alone, but the connector sees all Provider ⇄ kcp traffic in plaintext, PM gets another key to manage, and two handshakes per stream. Unnecessary once the owner's workspace is the trust boundary.
- **A raw pinned connection key** instead of an owner CA. Works, but needs a key rotation protocol (`PUT /key` with pending keys) for routine use, and gives the owner no way to keep the identity durable outside the Secret.
- **Re-onboarding existing connections with an onboarding token.** Lets outsiders take over a connection (finding 7).
- **Application-level signatures** (v1's DPoP-style proofs). Work through any ingress, but are custom crypto and need payload encryption (HPKE) for confidentiality past a terminating hop. TLS inside a WebSocket gets both from standard TLS 1.3.
- **Other ways to tunnel TLS through an ingress** (HTTP `CONNECT`, HTTP/2 extended `CONNECT`, raw TCP upgrades). Less widely supported than WebSockets.
- **v3, kcp SA tokens as the only credential.** Every connection depends on kcp's SA signing keys, which rotate without overlap in kcp-operator deployments (finding 4).
- **Revocation through CRLs or OCSP.** Not needed: the Provider-side checks the connection record on every handshake.

## Open items

- **Ingress limits for WebSockets.** Document what Providers must check: idle timeouts, maximum connection age, maximum frame or message size, and WAF behaviour on binary frames. Pick a session ping interval that fits common defaults.
- **The verification helper.** One small, tested implementation of both callbacks (client-side pinning of `serverKeys`, server-side per-connection owner-CA verification), shipped in the Provider SDK and used by the connector.
- **Owner CA parameters.** Default key type and lifetime, connection certificate lifetime, and how much clock skew the Provider-side tolerates.
- **Owner-supplied CAs.** Whether the owner may supply an intermediate from their organisation's PKI (and whether the Provider-side then pins the intermediate or the root), and how the request validates it.
- **Token requirement for anchor rotation.** Whether `anchorRotationRequiresToken` should be recommended by default, given that rotations are rare and a stolen CA can otherwise lock the owner out. Also the pending-CA expiry and how quickly old-CA sessions are closed after promotion.
- **Server key rotation.** The overlap period, whether `GET` announces retirement dates, and rate limits on the `server-keys` refetch.
- **Garbage collection of orphaned connections** on the Provider-side (no sessions for N days), and how owners delete them in the portal.
- **State migration between connections.** Whether Providers should offer an owner-consented migration after a lost owner CA, and what the RFC says about it.
- **Which CA bundle the connector sends.** Its own kubeconfig's CA for `frontProxyURL` covers the front-proxy; confirm what covers shard virtual-workspace hosts in PM's setups.
- **Readiness gate timeout.** How long the request waits in `VerifyingKcp` before failing, and how the Provider-side reports TLS errors in `lastError` without leaking details.
- **Provider-side token self-rotation.** Whether to enable it by default after the claim.
- **Non-exportable owner CA keys** (KMS or HSM). Possible because the connector only needs a few signatures per day; worth it if the connector's blast radius becomes a concern.
- **Fix in kcp-operator: drop `--service-account-lookup=false`.** Finding 2. kcp has supported cross-shard lookup since v0.32. That would bring back SA deletion as revocation, within about a minute, for every version of this design and for RFC 006. Confirm the flag on a running PM cluster first.
- **Connector placement.** As in v2. It holds the owner CAs of every connection it serves, which makes it the highest-impact target (see "Threat model").
- **Tunnel library.** As in v2, plus: confirm that remotedialer or Konnectivity runs unchanged over an inner TLS connection (it should: they only need a `net.Conn` or an HTTP server).
- **Provider-side multi-replica**, **`direct` mode**, **addressing changes** (`clusterID`, `frontProxyURL`), **request permissions**: as in v2.

## Prior art

- **kubeadm bootstrap tokens:** `tokenID.tokenSecret`, stored hashed, short-lived.
- **Kubernetes CSR-based node bootstrapping (kubelet TLS bootstrap):** a bootstrap token, then a certificate-based identity with automatic rotation.
- **SSH host keys and SSH certificate authorities:** a pinned server key, and client identities issued from a CA the verifier trusts.
- **Tunnelling a protocol through a WebSocket to get past L7 proxies:** Chisel (SSH over WebSocket), Rancher `remotedialer`; Teleport's connection upgrade for L7 load balancers is a similar idea.
- **Rancher `remotedialer`** and **Konnectivity (apiserver-network-proxy):** multiplexed reverse tunnels with dial callbacks.
- **Railgrid edges provider:** Lease-based tunnel routing; write-once SSH host-key pinning; also the power-off budget of refresh-by-presenting-itself.
- **Open Cluster Management:** bootstrap kubeconfig, then CSR-based registration; cluster-proxy for the reverse tunnel.
