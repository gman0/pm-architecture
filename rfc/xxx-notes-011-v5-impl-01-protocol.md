# v5 implementation plan: protocol

Part of the [v5 implementation plan](./xxx-notes-011-v5-impl-00-overview.md). The wire contract between the PM-side (the [operator](./xxx-notes-011-v5-impl-03-providerconnections-operator.md) and the [connectors](./xxx-notes-011-v5-impl-05-connector.md)) and the Provider-side (the [SDK](./xxx-notes-011-v5-impl-07-provider-sdk.md)). Both sides implement exactly this document; neither relies on anything the other does beyond it.

## Principles

- **Everything that grants anything travels inside inner TLS.** Plain HTTPS carries only the onboarding token (single-use, spent on first use) and public material.
- **The Provider-side is the verifier of every PM credential**; PM verifies the Provider-side by pinned server keys. Neither side needs the other's CA infrastructure beyond pinned material.
- **Every request is idempotent or safely retryable**, and responses carry nothing secret.
- **The protocol is versioned** from the first release, and every message is forward-compatible (unknown fields ignored).

## Endpoints at a glance

All paths are relative to the Provider's **base URL** from the onboarding token.

| Endpoint | Transport | Caller | Authenticated by | Purpose |
|---|---|---|---|---|
| `POST /v1/connections` | plain HTTPS | operator | onboarding token | Register a connection |
| `POST /v1/connections/{id}/rebind` | plain HTTPS | operator | onboarding token | Start recovery after a lost connection Secret |
| `GET /v1/connections/{id}/server-keys` | plain HTTPS | operator | none (web PKI) | Re-read server keys after a missed rollover |
| `GET /v1/connections/{id}/control` | WebSocket + inner TLS | operator | inner TLS: pinned server key (server); connection secret inside (client) | Control calls |
| `GET /v1/connections/{id}/session` | WebSocket + inner mTLS | connector | outer: session assertion; inner TLS: shard certificate (client), pinned server key (server) | A session carrying the multiplexer |

Plain-HTTPS endpoints are verified with web PKI on the base URL, or with the `Provider`'s `spec.remote.caBundle` when set.

## Onboarding token

- **Format**: `pm1.<base64url(base URL)>.<tokenID>.<tokenSecret>`. The base URL inside ensures the token is only ever sent to its issuer.
- **Single-use and short-lived**; the Provider-side stores only a hash of `tokenSecret`.
- **Bound to the issuing owner account** on the Provider-side, which the rebind check relies on.
- **Spent on first successful `POST`**, but a retry with the same idempotency key and secret hash within a bounded window returns the same result (see "Idempotency").

## Connection secret

- **Generated by the PM-side**: prefix plus 256 random bits, `pmc1_<base64url>`. The prefix lets secret scanners recognise it.
- **Only its hash crosses the wire** at registration and rotation (`sha256:<hex>`). High entropy makes a plain SHA-256 sufficient.
- **Used only inside control sessions**, never on plain HTTPS.

## Registration

Request: idempotency key (the `ProviderOnboardingRequest` UID), `clusterID` (logical cluster of the provider workspace), front-proxy URL, the secret's hash, the session CA certificates (current generations), and the protocol versions the PM-side supports.

Response: `connectionID`, the Provider-side's **server keys** (public keys, a list to allow rotation), and the chosen protocol version.

Rules:
- **Only new connections.** Registration never changes an existing connection.
- **Idempotency**: keyed on `(tokenID, idempotencyKey)`. A retry with the same `secretHash` returns the same `connectionID`; a different hash is refused. After the token's expiry, a retry is still honoured for a bounded window.
- **Addressing is immutable**: `clusterID` and front-proxy URL are fixed for the connection's life.
- **Trust in the response** comes from web PKI on the base URL; it's what makes the returned server keys safe to pin.

## Control sessions

A WebSocket upgrade on `/v1/connections/{id}/control`, then a TLS 1.3 handshake inside the WebSocket:
- **Server**: the Provider-side presents a self-signed certificate for one of its server keys; the operator accepts only keys pinned for this connection.
- **Client**: no client certificate. The operator sends the connection secret as a bearer credential on each request inside the inner TLS.
- **Inside**: HTTP (HTTP/2 preferred via ALPN, HTTP/1.1 allowed), carrying the control calls.

Control calls:

| Call | Effect |
|---|---|
| `GET /v1/connections/{id}` | Status (see "Status"), server keys, pinned session CA fingerprints, pending secret flag, pending rebind |
| `PUT /v1/connections/{id}/secret` | Stage a new secret hash; promoted on first successful authentication with the new secret |
| `PUT /v1/connections/{id}/session-cas` | Replace the pinned session CA certificates (rollover) |
| `DELETE /v1/connections/{id}` | Delete the connection; all its sessions close |

- **Any successful authentication with the current secret cancels a pending rebind.**
- **A staged secret** is accepted alongside the current one until promoted, and expires if never used.

## WebSocket framing

Applies to control sessions and sessions alike, so that they pass common edges (ingresses, load balancers, CDNs, WAFs) unchanged:
- **Binary messages only.** Everything inside is TLS ciphertext; text messages are a protocol error and close the connection.
- **At most 32 KB per message**, in both directions. TLS records are at most 16 KB anyway; the cap keeps every message under common edge limits. A larger message is a protocol error.
- **Pings at the outer level** at a fixed interval (e.g. 30 seconds), so idle timeouts above that never fire.
- **No reliance on message boundaries**: the inner TLS is a byte stream over the messages; either side may split or coalesce.
- **Only the upgrade request is plain HTTP.** It's an ordinary `GET` with the `Upgrade: websocket` handshake, from a non-browser client: no cookies, no JavaScript. Edges must not answer it with a bot challenge.

## Diagnosing the edge

Most onboarding problems come from the Provider's edge, not the protocol. The PM-side classifies failures on the first control session after registration, and on every reconnect, and reports them with distinct reasons ([03 Operator, "Readiness and health"](./xxx-notes-011-v5-impl-03-providerconnections-operator.md)):
- **upgrade refused** (a non-`101` response), including **an HTML page in response**, the typical sign of a bot challenge or WAF block page;
- **connection closed right after a binary message**, the typical sign of a WAF inspecting WebSocket payloads;
- **connection closed at a regular age or after a regular idle time**, the sign of an edge timeout below what the protocol needs.

The SDK also offers Providers an edge self-test against their own base URL ([07 SDK, "Edge self-test"](./xxx-notes-011-v5-impl-07-provider-sdk.md)), using an optional endpoint:

| Endpoint | Transport | Authenticated by | Purpose |
|---|---|---|---|
| `GET /v1/edge-check` | WebSocket | a test secret configured only on the Provider-side; disabled when none is set | Echo binary messages up to the size cap, and hold the connection open, so the self-test can measure the edge |

## Sessions

### Outer layer

A WebSocket upgrade on `/v1/connections/{id}/session` with `Authorization: Bearer <session assertion>`.

The **session assertion** is a JWT signed with the shard certificate's key:
- header: algorithm, and `x5c` with the shard certificate (and at most one intermediate, reserved for later);
- claims: `aud` = this connection's session URL, `cluster` = the provider workspace's `clusterID`, `sub` = an opaque session-group ID for audit, `iat`, `exp` (at most 5 minutes after `iat`), `jti`.

The Provider-side verifies, in order:
1. the `x5c` chain against **only** the connection's pinned session CA certificates, with at most one intermediate, checking validity, CA constraints and the shard certificate's key usages (signing and client authentication);
2. the JWT signature with the shard certificate's key;
3. `aud` exactly, `iat` and `exp` within a **clock-skew tolerance of 1 minute**, `exp − iat` ≤ 5 minutes, and `jti` not seen within its validity (so the replay cache keeps entries for about 6 minutes);
4. `cluster` equals the `clusterID` stored at registration.

### Inner layer

After the upgrade, a TLS 1.3 handshake inside the WebSocket:
- **Client**: the connector presents its shard certificate. The Provider-side requires it to be **the same certificate** as the assertion's `x5c` leaf, which binds the inner handshake to the verified assertion.
- **Server**: the Provider-side presents a self-signed certificate for one of its server keys; the connector accepts only keys pinned for this connection (read from the `ProviderEndpoint`, see [02 APIs](./xxx-notes-011-v5-impl-02-apis.md)).
- **ALPN** names the session protocol and version (e.g. `pm-session/1`), so a future change is negotiated, not guessed.

### Multiplexer

- **yamux** runs inside the inner TLS.
- **Only the Provider-side opens streams.** The connector refuses streams it didn't expect and never opens any.
- **Each stream starts with a length-prefixed binary preamble naming its target**: a version byte, a 2-byte length, then `host:port`, with a small maximum length. Plain HTTP/1.1 follows. The connector checks the target against its allow-list before reading any HTTP ([05 Connector, "Proxying"](./xxx-notes-011-v5-impl-05-connector.md)), and requires each request's `Host` to match the preamble.
- **Flow control per stream** is required: a slow reader on one stream must not stall others or force unbounded buffering.
- **Go-away**: the connector signals graceful replacement with yamux's go-away; the Provider-side stops opening streams on that session and lets in-flight ones finish.
- **Liveness**: WebSocket pings at the outer level (so ingresses see traffic), yamux keepalives inside.

### Hosts a session serves

- The hosts named in the shard certificate (its shard's virtual-workspace host).
- The connection's front-proxy host, on every session.

## Rebind

`POST /v1/connections/{id}/rebind` with a fresh onboarding token and a new secret hash:
- accepted only if the token's owner is the connection's owner;
- starts a waiting period (**72 hours by default**, configurable on the Provider-side) and returns when it completes;
- **cancelled by any successful control-session authentication with the current secret** during the waiting period; sessions don't count;
- on completion, the new hash replaces the old one; the `connectionID`, pinned session CAs, server keys and all Provider-side state stay.

## Server keys

- **A list**, so the Provider-side can rotate with overlap: a new key is announced in `GET` before it's used, the old one retired after the overlap.
- **`GET …/server-keys`** on plain HTTPS returns the current list. It's only used after pinned keys fail (a missed overlap), and is as trustworthy as registration.

## Status

`GET /v1/connections/{id}` returns, per host the Provider-side actually needs (the front-proxy, plus each endpoint-slice host its clients use):
- the number of live sessions covering it;
- whether its last requests reached kcp;
- the last error, without sensitive detail.

The operator turns this into aggregate conditions ([03 Operator, "Readiness and health"](./xxx-notes-011-v5-impl-03-providerconnections-operator.md)). No shard names or PM topology appear.

## Errors and retries

- **Authentication failures** return a uniform response without detail; the Provider-side records the reason for its own audit and notifications.
- **Rate limits** return `429` with `Retry-After`; the PM-side honours it with jitter.
- **Transient failures** (`5xx`, connection errors) are retried with backoff; registration and rebind retries reuse the same idempotency key and hash.
- **A deleted or frozen connection** refuses everything with a stable, distinguishable status, so the PM-side can report it instead of retrying forever.

## Versioning

- **Path version** (`/v1`) for the HTTP endpoints, **ALPN** for the session protocol.
- **Compatibility window: current and previous version.** The SDK and every PM-side component support both.
- **Negotiated independently per channel**: registration negotiates the HTTP API version (path version) and stores it for control calls; each session negotiates its own version through ALPN. Connectors and SDKs can therefore be upgraded independently, without re-registering connections.
- **Upgrading a connection's control-call version** happens on the next control session after both sides support the newer one; no new registration.

## Deliverables

- **This contract as a versioned specification** in the SDK module, with the message schemas.
- **Test vectors**: valid and invalid assertions (expired, wrong `aud`, wrong `cluster`, foreign chain, missing EKU, too-long chain, replayed `jti`), inner-TLS mismatches (client certificate not equal to the assertion leaf, unpinned server key), stream preambles outside the allow-list. Shared by the SDK and the connector's tests ([10 Testing](./xxx-notes-011-v5-impl-10-testing.md)).

## Decided

- Compatibility window: current and previous version, negotiated per channel (see "Versioning").
- Clock-skew tolerance: 1 minute.
- Rebind waiting period: 72 hours by default.
- Stream preamble: length-prefixed binary.
- Rate limits on registration and rebind per owner: SDK defaults, configurable by each Provider ([07 SDK](./xxx-notes-011-v5-impl-07-provider-sdk.md)).
